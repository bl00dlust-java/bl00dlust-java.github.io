## Подтверждённое состояние проекта

### Технологии и точки входа
- Используются React 18, TypeScript 5, Vite 6 и Tailwind CSS 3.
- Vite собирает `index.html` и `admin/dashboard.html`.
- `admin/dashboard.html` подключает React-панель через `src/admin-main.tsx`.
- Публичная страница `index.html` продолжает использовать статические HTML/CSS и браузерные скрипты из `js/`.
- React-прототип публичного интерфейса в `src/react-app.tsx` существует, но не подключён к корневому `index.html`.
- Курс, дополнительные разделы и часть редакторов используют старую статическую реализацию.
- В проекте сосуществуют две реализации интерфейса. Это технический долг, но не основание немедленно удалять старые страницы.

### Контент и хранение данных
- Учебные материалы и сценарии хранятся в JSON-файлах в `data/`.
- Прогресс и настройки сохраняются локально в браузере.
- Облачной базы пользователей и синхронизации между устройствами нет.
- GitHub Pages публикует статический сайт и сам по себе не предоставляет защищённый backend.

### Административная панель и безопасность
- Существующая панель использует GitHub Contents API.
- Владелец вручную вводит GitHub-токен; просмотренный код хранит его в памяти страницы, а не в виде константы в репозитории.
- Это не серверная авторизация и не система ролей. Скрытая ссылка или `noindex` не защищают административную страницу.
- Первичный поиск по репозиторию не обнаружил очевидных токенов в исходниках, но это не является полным secret scan.
- В проекте встречается `innerHTML`; сам факт его использования не доказывает XSS. Необходимо отдельно проследить источники данных и контекст вставки.
- Успешный CodeQL — полезная автоматическая проверка, но не гарантия отсутствия уязвимостей.

## CI и подтверждённые проверки

## Основные риски и приоритеты

1. **Дублирование публичного интерфейса.** Сначала определить целевую точку входа и границы модулей; мигрировать постепенно.
2. **Административный токен.** Не расширять текущую схему до публичной системы администрирования. Использовать токен с минимально необходимыми правами и только на доверенном устройстве.
3. **Неполное тестовое покрытие.** Текущие CI-проверки не являются полноценными пользовательскими функциональными тестами.
4. **Зависимости без lockfile.** В корне репозитория нет `package-lock.json`; диапазоны версий с `^` и установка через `npm install` могут давать разные деревья зависимостей. Lockfile следует создать штатной установкой npm в контролируемой среде, затем перевести CI на `npm ci`.
5. **Визуальная и мобильная проверка.** Необходимо проверить реальные страницы, меню, формы, темы, размеры экранов и консоль браузера.
6. **Потоки данных и XSS.** Требуется адресная проверка мест, где данные попадают в HTML, включая материалы, редактируемые через админку.
